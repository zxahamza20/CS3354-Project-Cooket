# Database Docs

## What it does

Scraped recipes are stored in Supabase (Postgres) so repeat searches don't have to scrape again. A live scrape takes 2 to 6 seconds, a database lookup takes about 0.1 seconds (see `spikes/S-01`), which is what lets cached searches meet QR-01's 3 second target.

The database is optional. If the Supabase keys aren't set, or Supabase is down, every search just scrapes live like before.

## Setup

The team shares one Supabase project, ask the database owner for the URL and secret key. Add them to backend/.env next to the Tavily key, and don't commit it.

```
SUPABASE_URL=https://your-project-id.supabase.co
SUPABASE_SECRET_KEY=sb_secret_your_key_here
```

Use the project URL with nothing after `.supabase.co`, and the secret key (starts with `sb_secret_`), not the publishable one. Only the backend talks to Supabase, the browser never sees the key.

To create the tables in a new Supabase project, paste `backend/db/schema.sql` into the Supabase SQL Editor and run it once.

## Schema

One table, `recipes`. Columns match what `extractRecipe()` returns so stored recipes can go straight into `rankRecipes()`.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid | Generated by the database |
| url | text | Unique, so the same page is never stored twice |
| title | text | "Untitled recipe" if the site didn't give one |
| ingredients | text[] | Ingredient lines as scraped |
| ingredients_search | text | Ingredient lines joined into one lowercase string, this is what searches run against |
| steps | text[] | Empty list if no steps were found |
| text | text | Description, keywords, category, cuisine. Used for tie-breaking |
| created_at | timestamptz | When the recipe was first stored |

Row Level Security is on with no policies, and the backend's `service_role` only has select, insert and update (no delete). The public key can't read or write anything.

## How a search uses it

Code is in backend/db, called from `scrapeRecipes()` in backend/routes/webscrape.js.

- client.js: creates the Supabase client, or null if the keys aren't set
- recipes.js: `findStoredRecipes()` and `saveRecipes()`
- schema.sql: the table, RLS and grants

1. `findStoredRecipes()` loads up to 50 stored recipes whose `ingredients_search` contains any of the searched ingredients, with plural endings dropped so "tomatoes" also finds "tomato".
2. Those candidates go through `rankRecipes()` from score.js. If at least 3 of them get a matchScore of 100 (`MIN_FULL_MATCHES`), they're returned, no scraping. Using score.js here means the database and the results always agree on what counts as a match.
3. Otherwise it scrapes live, `saveRecipes()` upserts the results on `url` (new pages are added, pages seen before are updated), then they're ranked and returned.

Recipes are saved before ranking because `rankRecipes()` drops the `text` field, and stored recipes need it for tie-breaking like scraped ones.

If a lookup or save fails, it's logged in the server console and the search carries on with live scraping, so Supabase being down slows searches but never fails them (risk R1). The API format doesn't change, see Scraper.md.

## Design decisions

- One table with a lowercase search string instead of separate normalized ingredient tables. The scraper gives us full lines like "2 slices bread", and nothing turns those into clean names yet, so the database does a quick contains search on one string to find candidates, and score.js does the accurate whole-word matching. A normalized ingredient list would let the database do the accurate matching itself, and is the next step once ingredient normalization exists (risk R2).
- Cache in Supabase rather than in server memory. Memory is lost on every restart and isn't shared if we run more than one server, Supabase was already our chosen database.
- Fall back to scraping instead of showing an error when Supabase is unavailable, since scraping still gives the user results.
- Require 3 recipes that use every ingredient before skipping the scrape. Using "any ingredient" would let egg-only recipes answer a search for "egg, bacon", and a lower number would mean we stop finding new recipes for a search after the first one. We picked variety over speed.
- Upsert on `url` instead of skipping existing rows, so a re-scraped recipe picks up any changes from the site.

## Current limitations

- The cache rarely kicks in yet. Most scrapes only keep 1 to 3 recipes (lots of 403s and video links), so a search needs to be scraped a few times, or overlap with other searches, before 3 full matches build up. In the S-01 spike only 1 of 3 searches reached it. Lowering `MIN_FULL_MATCHES` in recipes.js to 1, or remembering which searches were already scraped, would make it kick in sooner.
- Stored recipes never expire. A recipe only refreshes when a search falls through to scraping and finds that page again. `created_at` is there so old recipes could be ignored later.
- The database search is a loose contains check, so a search for egg also loads eggplant recipes as candidates. score.js filters those out of the full-match count, but they still use up some of the 50 candidate slots.
- Only the first 50 matching recipes are looked at, so with a big table some full matches could be missed.
- There's no cap on how many recipes get stored, the free tier allows 500 MB which is a lot of recipes, but usage should be checked on the Supabase dashboard (risk R7).
